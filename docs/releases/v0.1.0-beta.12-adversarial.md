# Ronda adversarial de `subject_ref` v1 (`v0.1.0-beta.12`)

## Alcance

Candidata `v0.1.0-beta.12` para el gate G-SUBJECT (issue #59 / ADR-0033):
identidad contextual estable `subject_ref`, binding bajo `write_lock`, comando
de resolución `subject namespace`, schema `subject-namespace-result-v1`,
`capabilities()` aditivo, metadatos de release y preserve del contexto
gestionado beta.11. Se ataca la candidata acumulativa sobre la base `827f943`
(commits de Fase 0/A/B/C/D + E1 sin commitear).

## Modelo de amenazas

- **Memoria recuperada / confused deputy:** `subject_ref` hereda la frontera de
  `AGENTS.md` / `AN-KLA.md` (dato, nunca instrucción ni autoridad). No entra en
  `_SELF_ASSERTED_AUTHORITY_KEYS`; `evaluate_write` no lo lee para decidir techo.
  El binding no eleva autoridad; el namespace es derivado, no declarado.
- **Forma / longitud / cardinalidad:** regex anclada ASCII reject-only (sin
  NFC/casefold); namespace es digest `p-<32hex>`, no path/URL/UUID crudo. El
  schema `subject-namespace-result-v1` ahora declara `maxLength: 34` junto al
  pattern (Fase C L-1). Cardinalidad 0-1.
- **TOCTOU / reemplazo de anchor:** el binding corre bajo `write_lock`, después
  de `assert_unchanged` y `verify_write_plan`, antes de construir `pending`. Si
  la identidad migra entre `subject namespace` (sin lock) y commit, falla
  `IdentityError("store_identity_changed")` primero. El catálogo drift del
  resolver ahora incluye `identity_uuid_invalid` (Fase C L-3): carrera con UUID
  corrupto → fail-closed exit 3.
- **Cross-project / disclosure:** namespace es digest; correlación dentro/entre
  stores del mismo project-identity, no privacidad adicional. Sin namespace
  cross-project en v1 (stop-condition).
- **Fingerprint drift:** nuevo validador `subject_ref` rotó `policy_fingerprint()`;
  planes stale → `write_policy_fingerprint_mismatch` vía `verify_write_plan`.

## Verificación de canonicidad / determinismo

- `SUBJECT_REF_PATTERN` se define una vez en `an_kla/subject_ref.py`; el
  `pattern` del JSON Schema en `docs/schemas/write-proposal-v1.schema.json` y en
  `an_kla/schemas/write-proposal-v1.schema.json` es el mismo string
  (verificación: `test_subject_ref_pattern_identical_in_code_and_both_schemas`).
- `subject-namespace-result-v1` byte-idéntico entre `docs/schemas/` y
  `an_kla/schemas/` (verificación: `test_schema_copies_are_byte_identical`).
- `policy_fingerprint()` rotado y congelado por nuevo golden tras Fase A.
- `capabilities()` canónica: dos invocaciones producen JSON idéntico
  (`test_capabilities_are_deterministic_and_describe_facts_only_v1`).
- `record_validators` mapping detached; mutar la copia devuelta no afecta
  `policy_configuration()` ni `policy_fingerprint()`
  (`test_record_validators_returned_mapping_is_unshared`).
