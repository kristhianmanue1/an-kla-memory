# Ronda adversarial de `supersede` gobernado (`v0.1.0-beta.8`)

## Alcance

Release completa que implementa ADR-0019 (`operation=supersede`) en tres fases
(PR-A política, PR-B storage, PR-C release). Se revisaron con subagente de
contexto fresco, en cuatro pasadas adversariales:

- el **diseño** (ADR-0019 v1 → v2);
- la **política pura** (PR-A, `write_policy.py`);
- un **spike pre-implementación** del storage (antes de codear PR-B);
- el **storage** (PR-B, `store.py`).

Además, PR-C (este release) toca el **contrato administrado**: bump de
`TEMPLATE_VERSION` + bloque gestionado vía flujo gobernado + release notes.

## Modelo de amenazas

`supersede` es la **primera operación que muta vigencia** (oculta el target de
`retrieve`), lo que abre un vector que `add` no tiene: el **silenciamiento** de
un fact vigente. La frontera de confianza exige (a) no borrar evidencia (el CAS
es inmutable) y (b) impedir que memoria recuperada (dato no confiable) silencie
facts. El release mitiga ambos: el contenido del target queda byte-idéntico
(overlay en memoria) y `derived_from_retrieval` no puede `supersede` (decisión
pura en `evaluate_write`, re-validada bajo lock vía `verify_write_plan`).

| Fase | Hallazgo | Riesgo | Corrección |

## Verificación de canonicidad / determinismo

- `policy_fingerprint()` cambia por los **4 vectores** declarados
  (`supported_operations`, `derived_authority.allowed_operations`, `reason_codes`,
  `terminal_error_codes`); determinista y reproducible.
- El `supersedes_map` viaja dentro del manifest content-addressed (el hash del
  manifest lo cubre); el overlay de `snapshot()` es derivado determinista del
  mapa.
- El CAS del target permanece inmutable (`O_EXCL`); verificado que el segment_id
  y los bytes del target no cambian tras supersede.
- `verify()` sigue reportando presencia física (incluye sustituidos); la
  vigencia es una capa observable derivada, no física. Documentado.

## Límites declarados

- `refute` y `decay` siguen fuera (producen `skip` con `operation_not_supported`).
- `supersedes` es **1-a-1** en beta (un id por proposal, no lista); flexibilidad
  futura requeriría ADR adicional.
- `eliminada` sigue sin operación gobernada.
- `lineage.refs` al target sustituido quedan como soft-orphan (los segments son
  inmutables; trazar vía revisions).
- `_validate_manifest` no exige claves exactas por entrada del mapa (LOW;
  inalcanzable por content-addressing).
- El `supersedes_map` es acumulativo y sin cota; un ADR futuro podría podar
  entries resueltas (target y sustituida_por ambos sustituidos).
- Comment stale en `write_policy.py:421` («only supports add») — deuda declarada
  cosmética (follow-up).
