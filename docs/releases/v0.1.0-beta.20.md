# `v0.1.0-beta.20`

Beta.20 cierra la **fase H de hardness del issue
[#102](https://github.com/kristhianmanue1/an-kla-memory/issues/102)**
(reportada por el consumidor real infosalud) e incorpora el trabajo
gobernado de anclaje H1c (ADR-0044) y el threat model del store
(ADR-0043). Sin cambios de formato físico, de política de autoridad ni
del contrato `plan-write → commit-write-plan` (fingerprint estable); los
stores beta.19 se leen sin migración.

El contexto gestionado y la plantilla administrada permanecen en
`0.1.0-beta.11`.

## Cambios principales

- **H1 — validación temprana en `plan-write`** (#103): `plan-write`
  falla cerrado con códigos estables `plan_duplicate_id`,
  `plan_supersede_target_missing`, `plan_supersede_target_not_vigente`
  (nuevo módulo `an_kla/plan_guard.py`). La resolución autoritativa bajo
  lock en commit se conserva (ventana TOCTOU); el policy core permanece
  puro y `policy_fingerprint` no cambia. Los códigos están declarados en
  `capabilities()` (`write_policy.plan_time_error_codes`) y pineados por
  test.
- **H2 — registro sin texto indexable visible** (#104):
  `commit-write-plan` añade `record_without_indexable_text` a
  `outcome.warnings` (campo existente de `commit-outcome-v2`). El
  planning-result no cambia (gate de claves exactas intacto).
- **H4 — diagnóstico diferenciado de fence** (#105): los marcadores
  anclados dentro de una cerca de código sin cerrar producen
  `managed_block_inside_fence` (antes: `managed_block_structure_invalid`
  genérico, indistinguible de corrupción). Bug real del consumidor.
- **H6 — Python 3.13**: verificado por el consumidor (suite verde en
  3.13.5); badge y matriz local actualizados.
- **H7/H8 — hooks y CI local-only**: plantilla de hook `pre-commit`
  disciplinario en `docs/hooks-template/` (instalación vía
  `core.hooksPath`, doble defensa del update-check) y principio
  documentado de verificación sin CI remota.
- **CI remota retirada** (decisión del operador, beta.20): el repo no
  define workflows de GitHub Actions; la verificación canónica es local
  (`scripts/ci_local.py --simulate-ci` + gates de tamaños y registro).
  `test_ci_metadata` congela la política invertida: si un workflow
  reaparece, obliga a re-pinear acciones a commits revisados.
- **ADR-0043 (threat model del store)** y **ADR-0044 (formalización H1c
  débil-con-anclaje)** con `scripts/verificar_anclaje.py` y suite de
  red-team; el `--selftest` del red-team queda como deuda de gate
  (issue de seguimiento).
- **ADR-0045 — adopción de Skevi como estándar de proceso** (PRs #107/#108,
  mergeados en remoto durante el ciclo): corpus `.skevi/`, guía
  F0→F3 en `docs/ai-agent-guide/`, capa normativa transversal, plantillas
  en `templates/` y el nuevo gate `scripts/check_plans.py` (estructura
  E1–E5 de planes), integrado a `scripts/ci_local.py`. Registro vigente en
  `AGENTS.md`.
- **Docs de planning**: planes técnicos + rondas adversariales de
  #102 (attest+hardness) y #56 (G2 host-hooks); fixes pequeños H1/H2/H4
  extraídos como #103–#105 (cerrados en este ciclo).

## Cambios de comportamiento observables

1. `plan-write` puede fallar ahora con `plan_duplicate_id` /
   `plan_supersede_target_missing` / `plan_supersede_target_not_vigente`
   donde antes producía un plan y el error aparecía en commit. Flujos que
   matcheaban `invalid_supersede_target`/`duplicate_facts_id` en commit
   deben manejar los códigos nuevos en plan (los de commit siguen
   alcanzables en la ventana TOCTOU).
2. Documentos con marcadores gestionados dentro de un fence sin cerrar
   reportan `managed_block_inside_fence` en lugar de
   `managed_block_structure_invalid`.
3. `outcome.warnings` puede incluir `record_without_indexable_text`.
4. `plan_write` lee el snapshot base (antes sólo CURRENT): coste de
   lectura mayor por planificación; puede bloquear brevemente durante una
   compactación concurrente (reader gate).

## Límites

- Windows permanece diferido: el protocolo de anclaje usa un pipeline
  POSIX; `test_verificar_anclaje` se salta con degradación declarada en
  win32.
- El `--selftest` del red-team (ADR-0043) no está cableado a ningún gate
  automático (deuda con issue); el mensaje canónico no cubre ambos modos
  de fallo.
- El protocolo de anclaje es sensible a locale (`sort -k2` sin
  `LC_ALL=C`): verificar entre máquinas distintas puede requerir fijar
  locale (decisión pendiente del dueño; implica re-anclar).
- H3/H5 de #102 quedan como tareas de repro con el consumidor; attest
  (Fase A) y G2 (#56) esperan decisiones F0 del maintainer.
- El texto del contrato gestionado (`context_text.py`) no menciona
  `managed_block_inside_fence`; se difiere a un bump de plantilla para no
  mezclar cambio de plantilla con hardening.
