# AN-KLA Memory v0.1.0-beta.8

Versión del código: `0.1.0b8`. Etiqueta de distribución: `v0.1.0-beta.8`.
`TEMPLATE_VERSION` pasa de `0.1.0-beta.6` a `0.1.0-beta.8`: esta release **sí**
modifica el contrato administrado (primera vez desde beta.6).

## Resumen

Release que **gobierna `operation=supersede`** end-to-end (ADR-0019, issue #17).
Hasta beta.7 el modelo de vigencia definía el estado `sustituida` sin operación
ejecutable: una corrección se escribía como *fact nuevo al lado* del obsoleto,
dejando dos facts contradictorios coexistiendo como vigentes. beta.8 permite
sustituir un registro de forma gobernada: escribe el nuevo y marca el target
como `sustituida` (oculto de la recuperación), sin mutar el contenido inmutable
del target. `refute` y `decay` siguen fuera (producen `skip` con
`operation_not_supported`).

Implementación en tres fases (PR-A política, PR-B storage, PR-C release):

- **PR-A (#34)** — política pura: `supported_operations` y
  `derived_authority.allowed_operations` → `["add","supersede"]`; co-ocurrencia
  `operation=supersede ↔ supersedes`; `derived_from_retrieval` **no** puede
  `supersede` (la memoria recuperada no silencia un fact vigente); reason
  `supersede_requires_non_derived_authority`; código `invalid_supersede_target`.
- **PR-B (#35)** — storage: `supersedes_map` (acumulativo, heredado) a nivel
  revisión + overlay de vigencia en `snapshot()` que marca el target
  `status="sustituida"` sin reescribir el segmento inmutable; guarda
  `invalid_supersede_target` en `commit_write_plan` bajo lock (target existe +
  vigente + mismo stream + no-self-ref); filtro de vigencia en `build_index`.

## Cambio de comportamiento

### `supersede` gobernado (issue #17)

Un `WriteProposal` con `operation="supersede"` y campo `supersedes: <id>`
(futuro `write-proposal-v1`, campo opcional) escribe el registro nuevo **y**
marca el target como `sustituida`. Reglas (ADR-0019):

- el target se identifica por `id`, único **dentro del stream**;
- debe existir, estar **vigente** y ser del **mismo stream** (los ejes no son
  intercambiables);
- `supersedes != record.id` (self-reference prohibida);
- `derived_from_retrieval` no puede `supersede`; `model_derived` → techo
  `summary` y autoridades confirmadas sí;
- el contenido CAS del target queda **inmutable** (overlay en memoria, nunca
  reescribe el segmento); las cadenas A→B→C dejan A y B `sustituida`, C vigente.

Casos terminales (código `invalid_supersede_target`, sin side effects): target
inexistente (`target_missing`), ya sustituida/no-vigente (`target_not_vigente`),
self-reference (`self_reference`).

## Implementación

- `evaluate_write` (pura, ADR-0007 preservado) decide autoridad + representación
  + operación, y excluye `derived_from_retrieval`. La guarda de existencia/vigencia
  vive en `commit_write_plan` bajo `write_lock`, contra `snapshot(observed)`.
- Secuencia de commit: `lock → CAS → revalidate → [GUARDA SUPERSEDE] → journal →
  objetos (registro nuevo + entrada supersedes_map) → CURRENT`. Atómica vía el
  mismo CAS-on-CURRENT existente.
- `_validate_manifest` valida el shape del `supersedes_map` (defensa en
  profundidad); las revisiones legacy sin el campo se leen como overlay no-op.

## Cambios de contrato

- `TEMPLATE_VERSION`: `0.1.0-beta.6` → `0.1.0-beta.8`.
- `content_sha256` (COMPACT): sin cambios (`sha256:08e4d63…`; el payload compacto
  no menciona la operación).
- `contract_sha256` (DETAILED): `sha256:f19ca1…` → `sha256:72865b…` (las
  secciones «Límite de la beta» y «Preparar y clasificar» ahora declaran
  `supersede` gobernado).
- `0.1.0-beta.6` registrada en `_KNOWN_CONTEXT_TEMPLATES` como plantilla
  histórica conocida (permite migrar a quienes están en beta.6/beta.7).
- `policy_fingerprint()` cambia por **4 vectores** (corrección sobre el borrador
  inicial del ADR-0019 que decía 3): `supported_operations`,
  `derived_authority.allowed_operations`, `reason_codes` (+) y
  `terminal_error_codes` (+).
- `capabilities().write_policy.supported_operations` → `["add","supersede"]`.

## Cambios de schema

- `write-proposal-v1`: campo opcional `supersedes` (string, id del target;
  co-ocurrencia `operation=supersede ↔ supersedes` exigida por el core).
- `write-plan-v1`: campo opcional `supersedes` en cada item de `records[]`.
- Ambos se abren **aditivamente** (`additionalProperties:false` se mantiene con
  la propiedad añadida); **no** se publica `write-proposal-v2`.

## Migración desde beta.6 / beta.7

Como el contrato administrado cambia, hay que actualizar paquete y contrato:

```bash
.venv/bin/python -m pip install --upgrade \
  "an-kla-memory @ git+https://github.com/kristhianmanue1/an-kla-memory.git@v0.1.0-beta.8"
.venv/bin/python -m an_kla --version
.venv/bin/python -m an_kla --project-root . context status
.venv/bin/python -m an_kla --project-root . context plan --operation update
.venv/bin/python -m an_kla --project-root . context update
git diff -- AGENTS.md AN-KLA.md
.venv/bin/python -m an_kla --project-root . context status
.venv/bin/python -m an_kla --project-root . verify
```

Quienes están en beta.6/beta.7 (plantilla reconocida) migran sin fricción. El
`content_sha256` del bloque no cambia; sólo el `contract_sha256` (AN-KLA.md) y
el `version` del marker pasan a beta.8.

## Ronda adversarial

Ver `docs/releases/v0.1.0-beta.8-adversarial.md`. Se hicieron **tres** rondas
adversariales (subagente de contexto fresco) más un **spike pre-implementación**
que validó el plan de storage contra el código real antes de codear:

- ADR-0019 (diseño): `fix-and-retry` (2 BLOCKER + 4 HIGH absorbidos en la v2).
- PR-A (política): `fix-and-retry` (1 MEDIUM de regresión) → `proceed`.
- Spike PR-B (pre-code): `proceed` con 2 refines obligatorios (`build_index`
  filtra vigencia; `supersedes_map` acumulativo).
- PR-B (storage): `proceed` (4 LOW, no bloqueantes).

Hallazgos materiales: la pureza de `evaluate_write` (la guarda no puede vivir
allí), el mecanismo de storage del overlay (los segments son inmutables), y la
exclusión de `derived_from_retrieval` (memoria recuperada no silencia facts).
