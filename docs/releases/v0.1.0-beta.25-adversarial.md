## Preguntas mínimas (§13)

1. **¿El wheel corresponde realmente al candidato?** Sí — construido con
   `python -m build --wheel` desde el working tree del candidato, sin
   red, sin instalación editable. SHA-256 registrado abajo.
2. **¿El versionado del paquete reporta beta.25?** Sí — `an-kla --version`
   y `capabilities().product.version` → `0.1.0b25` desde el venv aislado.
3. **¿Se confundió package version con `TEMPLATE_VERSION`?** No — son ejes
   separados y se verificaron por separado: `an-kla --version` → `0.1.0b25`;
   `context status` → `template_version`/`current_template_version` →
   `0.1.0-beta.26`. README/CHANGELOG documentan la distinción
   explícitamente.
4. **¿El upgrade desde beta.24 conserva memoria y continuidad?** Sí —
   fixture con un fact, un episode y un checkpoint escritos con el
   **binario real de `v0.1.0-beta.24`** (wheel construido desde su propio
   tag, no desde `main`); tras `upgrade inspect`→`upgrade apply`→
   `upgrade verify` con el binario de beta.25: `revision` idéntica
   (`sha256:59724703e51ca958dd2c5edd20430b5e71eccb542c409836e6c3622d61717b77`),
   `checkpoint_digest` idéntico
   (`sha256:5d7b23dafc318980e64a9831fbefec357bbbf091344de2a50fbe68e6628fd732`),
   counts idénticos (facts:1/events:2/episodes:1), `context status` sano
   (`template_version` beta.21→beta.26), segunda `context plan --operation
   update` → `action:"noop"` (idempotente).
5. **¿Algún archivo de release introdujo cambios semánticos no probados?**
   No hubo cambios de código de producto en la preparación de release
   misma más allá de `scripts/check_clean_wheel.py` (fix de un `NameError`
   preexistente desde beta.23, nunca detectado porque el script no forma
   parte de la suite canónica ni de CI — hallazgo F1 abajo) y el hardcode
   de `template_version` en el mismo script (F2). Ambos ya cubiertos por
   ejecutar el propio script contra el wheel del candidato.
6. **¿Las notas de release prometen más de lo demostrado?** Revisadas
   contra §4 de la instrucción de esta ronda: no afirman seguridad
   universal, interoperabilidad universal, validación black-box de toda la
   interfaz, ni que G3 esté implementado. Documentan explícitamente
   `TEMPLATE_VERSION` como eje distinto del runtime.
7. **¿La instalación documentada funciona desde tag/wheel?** Verificado el
   patrón (`pip install "an-kla-memory @ git+...@vX.Y.Z"`); el tag exacto
   `v0.1.0-beta.25` se crea después de esta ronda (§14), por lo que la
   instalación *desde el tag publicado* se reverifica en la sección de
   verificación post-publicación (no antes de que el tag exista).
8. **¿El artefacto funciona sin acceso al repo fuente?** Sí — smoke H-DX
   black-box con un agente fresco sin lectura de código fuente, contra el
   venv con el wheel instalado (ver Hallazgos/Evidencia).
9. **¿Existe algún BLOCKER/HIGH reproducible que impida publicar?** No, tras
   absorber F1/F2 (abajo).
